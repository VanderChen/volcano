## 1. 摘要

Volcano 现在为带拓扑约束的作业选域的做法是：同一层的每个候选域都真实试放一遍，再比分。本设计把它改成固定的三段。

1. **筛选**：去掉不可能的候选域。
2. **排序**：在试放之前把剩下的候选域排好。先比层，窄的在前；同层比分数，高的在前；分数相同按一个哈希键。
3. **验证**：按排好的顺序逐个真实试放，第一个放得下的就是结果。

排序用的分数就是现有插件给域打的分，主要一项是"把这个单元放进去之后，这个域有多满"。这个分数不依赖试放，所以先排序再验证选出的域与现在相同，试放次数从"候选域的个数"降到接近 1 次。

三段流程之外有两处补充，用来找回现行搜索漏掉的合法放置：

- 筛选时区分两类约束："整个单元必须装进某一个域"和"只是不许用某些域"。现行代码把后者也当成前者，所以反亲和排除一个域之后，作业不能同时使用剩下的几个域。
- 整个搜索找不到解时，把被挡住的子组提到前面，重试有限的几次。

主要结果（单元测试级，上游原型）：

| 目标 | 现行 | 本设计 |
| --- | --- | --- |
| 结果是否改变 | — | 700 个随机会话里逐 Pod 落位与"现行 + 固定并列"相同；另外 2800 次单作业场景运行（约 2200 个不同的场景）里，现行能调度的作业全部仍能调度，落位相同 |
| 成功路径的试放次数 | 等于同层候选域的个数 | 平均每次决策 1.06–1.20 次；排在第一的候选在 88%–95% 的决策里直接通过 |
| 1024 节点、20 个硬拓扑作业的 allocate 耗时（第一轮原型测得） | 2.00 s | 0.046 s |
| 存在合法放置却调度不了（982 个可行的单作业场景） | 39 个 | 4 个 |
| 同样的输入重复运行 | 40 次会话选出 4 个不同的机架 | 结果固定；每次决策有一张"排名 + 结论"的表 |
| 带待分配 DRA claim 的硬拓扑作业 | 得分最高的域不是最后试放的域时调度失败 | 胜者不再撤销后重放，同场景正常绑定 |

三条需要先知道的限制：

- **排序不改善失败路径。** 所有候选都放不下时，每个候选仍要试放一遍。资源必要条件能跳过它证明得了的那部分。
- **这不是全局最优。** 本设计只保证在给定评分表下为当前作业选到最好的可行域，并在找不到解时做有限的补救。与事后挑出的最好顺序相比，它在随机作业流里少调度 1.7 个百分点的容量（§6.3）。
- **证据只到单元测试。** 实施后必须在 Kind 上按 §9 的场景验证，包括用户报告的缺陷原样复现与修复。

本设计里有三项会改变约束的语义或选域的规则，需要分别批准：可用域语义（§4.2.2）、找不到解时的重试（§4.5）、SubGroup 作业在 Job 级的排序（§4.3.6）。其余步骤选出的域与"现行 + 固定并列"相同（§5.1），但有别的可见变化：并列从随机变为固定；带待分配 DRA claim 的硬拓扑作业从失败变为成功；不可调度时的状态文本和条件消息。逐项见 §8。

## 2. 背景

### 2.1 名词

| 名词 | 含义 |
| --- | --- |
| 域 | 一个 HyperNode，例如一个机架、一个可用区。域按层组成一棵树 |
| 层 | HyperNode 的 tier。数值越小域越窄。本文例子里 tier 1 是机架，tier 2 是 zone，tier 3 是整个集群 |
| 单元 | 被放置的对象：一个作业（PodGroup），或作业里的一个子组（SubJob，由 SubGroup 策略切出） |
| 硬拓扑 | 单元声明 `highestTierAllowed`：全部 Pod 必须落在不高于该层的同一个域里 |
| required 反亲和 | PodGroup 级的 required anti-affinity：不能使用已被匹配的 PodGroup 占用的域 |
| 候选 | 某个单元可以整体装进去的一个域 |
| 试放 | 在一个候选域里，用真实的谓词、节点打分和 `Statement.Allocate` 把整个单元放一遍。不提交，可以撤销 |
| 评分表 | 各插件通过 `HyperNodeOrderFn` 给候选域打的分 |

### 2.2 现行流程

入口是 allocate action 的 `allocateForJob`。走这条路径的有硬拓扑作业、带 SubGroup 策略的作业、带 PodGroup 反亲和的作业，以及 soft 拓扑作业。

```text
allocateForJob(作业):
  各插件给出候选域，按层从低到高分组
  对每一层，从低到高:
    对这一层的每个候选域 C:
      在 C 里试放整个作业        # 逐个 SubJob；每个 SubJob 内部再做同样的一层循环
      记下试放结果，撤销
    如果有候选试放成功:
      给成功的候选打分，取最高分  # 并列时随机
      把胜者的试放结果重放一遍
      返回
  所有层都没有解：作业本轮不可调度
```

这个流程有两个特点决定了后面的问题：分数在试放之后才用；选出的胜者要撤销后再重放。

### 2.3 现行流程的四个问题

数字来自未修改代码上的探测测试，两条基线分别取证。

**效率：成本与候选域个数成正比。** 一个 T 个任务的硬拓扑作业，同层有 R 个放得下的候选域时，触发 2·T·R+T 次 Allocate 事件，谓词调用是 R 倍。T=4、R=32 时每个任务被分配 65 次。每次事件都会调用所有插件的事件回调。

**过程说不清。** 4 个完全相同的机架，重复 40 次会话，选中的机架分布是 19、5、7、9（一次运行的结果，每次运行不同）。作业调度不了时，节点级的原因只来自一个候选域；在 dev-1.14 上取哪个域每次运行还可能不同。

**重放与有状态的插件不兼容。** 硬拓扑作业的 Pod 带一个待分配的 DRA ResourceClaim，有两个可行的域。当得分高的域不是最后一个被试放的域时，重放失败（`claim allocation not found for node`）。上游 20 次里失败 20 次。原因是每个任务只有一份调度状态，重放时读到的是最后一次试放留下的内容。

**漏解：存在合法的放置，调度器却找不到。** 用独立的暴力求解器对照，982 个存在合法放置的单作业随机场景里，现行搜索有 39 个调度不了。来源有三种：

| 类别 | 现象 | 例子 |
| --- | --- | --- |
| 可用域被当成容器 | required 反亲和排除域 A 之后剩下 B、C。作业只被分别放进 B 或 C 里试，从来没有试过同时使用 B 和 C | 用户报告的缺陷：四个单 Pod 子组应当分别落在 B、C 下的四个节点，实际 `2/4 tasks in gang unschedulable`。上游 master 上它的六个变体全部复现。dev-1.14 为这个缺陷加过一条专门的路径（下称"候选森林"），修了其中三个，另外三个仍然复现 |
| 子组互相挡路 | 子组按固定顺序放，前面的子组占掉了后面的子组唯一能用的位置 | 机架 a 只剩 1 个 CPU，机架 b 空闲。子组 X 两个机架都能放，子组 Y 只能放 a。X 先放就占掉 a，作业 0/2；Y 先放则 2/2。两条基线都复现 |
| 域内任务大小不一 | 任务按顺序逐个取分数最高的节点，小任务占掉了大任务唯一放得下的节点 | 39 个里有 4 个。没有拓扑约束的作业同样会遇到 |

### 2.4 此前的方案

此前的整合稿主张用一个"联合规划器"：共享索引、增量状态，加上带回溯和质量预算的联合搜索，后续再引入网络流或树 DP。本设计不沿用它，原因有三条。

- 联合回溯要求每个插件的事件回调和调度状态都能精确撤销。上面的 DRA 问题说明，现在连一次重放都不安全。
- 回溯打开之后，一次调度的过程无法用几句话复述，这与"过程可解释"的目标冲突。
- 调研的同类系统里，Kueue、KAI 和 Kubernetes 的 workload 级调度都不做联合回溯：一个子单元放不下就放弃当前候选。Koordinator 只支持单个 gang，没有多子单元的放置；Slurm 的多组件作业怎么处理没有核实 [调研-2]。

整合稿里与本设计不冲突的部分保留：决策对账的不变量、确定性并列、域资源的增量维护。

## 3. 设计目标

### 3.1 目标与验收口径

| 编号 | 目标 | 验收口径 |
| --- | --- | --- |
| G1 | 不丢可调度性 | 对同一个作业、同样的会话状态：现行能调度的，新流程也能调度，默认配置下落位也相同。跨周期：现行靠并列时的随机选择才能调度的作业，新流程仍能在若干个周期内调度（没有理论上界，实测见 §4.3.8） |
| G2 | 少漏解，并且用通用机制 | 每一类漏解对应一个不依赖具体场景的机制；与暴力求解器对照的漏解数下降 |
| G3 | 效率 | 成功路径上，试放次数不随候选域个数增长；失败路径上的额外开销有固定上限 |
| G4 | 过程可复述 | 相同输入得到相同结果；每次决策留下一张表，说明每个候选排第几、为什么、结论是什么 |
| G5 | 不改插件合同 | 谓词、节点打分、队列与配额、设备类插件不需要改动；选中的候选里每个任务只触发一次 Allocate 事件，不再撤销后重放 |
| G6 | 可分步上线 | 每一步有独立开关；不改变落位的步骤与改变行为的步骤分开审批 |

### 3.2 目标之间的先后

对正在放置的这一个作业，比较两个结果时按下面的顺序，前一项相同才看后一项。

1. 满足硬约束。
2. 能调度。
3. 所在的层更窄。
4. 分数更高。
5. 搜索成本更低。

这个顺序决定了哪里可以省、哪里不能省。各项的实现强度不同，这里先说清楚：

| 项 | 本设计做到什么程度 |
| --- | --- |
| 1 硬约束 | 精确。每个落位都经过真实的谓词验证 |
| 2 能调度 | 不比现行差（G1），并在固定的预算内补救。预算就是第 5 项给第 2 项设的上限：预算之外的解不找 |
| 3 层更窄 | 逐层贪心，与现行相同：一层全部失败就去更宽的层 |
| 4 分数更高 | 在给定的评分表下精确：选到的是该层分数最高的可行候选 |
| 5 成本更低 | 提前停止只发生在第 4 项内部，即同一层里已经有候选验证通过之后。它不会让第 2、3 项变差 |

找回漏解的两个机制服务于第 2 项。对单个作业而言，它们只改变现行调度不了的作业的结果；同一个周期里排在后面的作业可能受影响（§5.3 末尾、§10.2）。

### 3.3 非目标

- 跨作业的全局最优。作业之间仍按队列和优先级的顺序逐个放置。
- 域内逐任务选节点的方式。上面第三类漏解不在本设计处理范围内。
- 抢占、回收路径的重构。本设计只要求它们对约束的解释与分配路径一致（§7）。
- 新的 API 或 CRD。

## 4. 方案

### 4.1 总览

放置一个单元（作业或子组）的过程：

```text
筛选   各插件的硬约束 → 候选域，按层分组；每个被排除的域记一条原因
对每一层，从窄到宽:
  排序   这一层的候选按（分数从高到低，并列键从小到大）排好
  验证   按名次逐个处理:
           凭资源就能证明放不下 → 跳过，记下数字
           试放成功            → 这就是结果；保留这次试放，结束
           试放失败            → 撤销，记下原因，看下一个
所有层都没有通过的候选 → 有限重试（§4.5）；仍然没有 → 本轮不可调度
```

单元是嵌套的。验证一个作业的候选域 C，就是在 C 里依次放置它的各个子组；每个子组在 C 的范围内用同样的三段流程选自己的域。没有 SubGroup 策略的作业只有一个默认子组。

一个例子（只看 CPU）。机架 r0–r3 各有 4 个 8 核节点，共 32 核。作业要求全部 Pod 在同一个机架，2 个 Pod，每个 4 核。

| 机架 | 已用 | 空闲的分布 | 筛选 | 分数 | 名次 | 结论 |
| --- | --- | --- | --- | --- | --- | --- |
| r0 | 28 | 4 核 | 排除：总空闲 4 核，少于需要的 8 核 | — | — | — |
| r1 | 24 | 每个节点 2 核 | 保留：总空闲 8 核 | (24+8)/32 = 100 | 1 | 跳过：每个节点都放不下一个 4 核 Pod，最多放 0 个，需要 2 个 |
| r2 | 16 | 两个节点各 8 核 | 保留 | (16+8)/32 = 75 | 2 | 试放成功，选中 |
| r3 | 0 | 四个节点各 8 核 | 保留 | (0+8)/32 = 25 | 3 | 未评估 |

现行流程在 r1、r2、r3 各试放一遍，再比分，同样选中 r2。新流程只试放了 r2。r3 保持全空，留给之后需要整个机架的作业。

### 4.2 筛选

筛选只做排除，不改变顺序。它由三部分组成，前两部分现在就有。

#### 4.2.1 现有的两步

- **插件硬约束。** 每个插件通过 gradient 回调给出它允许的域。network-topology-aware 给出不高于 `highestTierAllowed` 的域；group-topology-affinity 去掉被 required 反亲和排除的域。框架对各插件的结果求交集。
- **总量检查。** 域内所有节点的空闲资源之和小于单元的最低需求时，排除这个域（`FilterGradientsByMinResource`）。

#### 4.2.2 约束分两类：容器与可用域

现行的求交集是按域的名字做的。这对"必须装进一个域"的约束是对的，对"不许用某些域"的约束是错的，§2.3 的第一类漏解就来自这里。本设计把约束分成两类。

| 类别 | 含义 | 例子 | 多个域之间的关系 |
| --- | --- | --- | --- |
| 容器 | 单元必须整体落在其中某一个域里 | 硬拓扑的 `highestTierAllowed`；required 的 SubGroup 亲和；单元已有 Pod 所在的域 | "或"：逐个尝试 |
| 可用域 | 单元只能使用这些域里的节点，不要求落在其中某一个域里 | required 的 PodGroup 反亲和 | "都可以用" |

组合规则只有一条：**候选 = 容器 ∩ 可用域**。

- 一个容器只要与可用域有交集就保留为候选，验证时只能使用交集里的节点。
- 容器的列表和层的先后仍由现有插件决定。可用域只收窄节点，不改变顺序。
- 可用域为空，或者任何容器与它都没有交集时，单元不可调度，并写明是哪条约束排除了哪些域。
- 总量检查和资源必要条件都按交集里的节点计算。否则会选中一个"空闲资源全在被排除部分"的域，进去之后却无处可放。Kueue 出过同类缺陷 [Kueue-15787]。
- 可用域是一个节点集合。有多个来源时取交集。它按单元生效：作业的可用域对它的所有子组生效，子组还可以有自己的可用域。
- 对可用域提供方的要求：改用可用域之后新增的候选，在层序上必须排在它按名字过滤时保留的全部候选之后。这样现在能调度的作业走的路不变。层序由窄到宽时，这等价于新增的候选都更宽。required 反亲和在这种层序下满足这一点：它现在保留的域都不高于比较层，比较层以上的域一律被拒绝，所以新增的候选都在比较层以上。这是 group-topology-affinity 的性质，不是框架保证的，实施时要有断言和单测（§9.1）。
- 已知的例外：dev-1.14 对带 preferred SubGroup 条目的作业改了 Job 级的层序（§4.3.1）。这类作业同时带 required 反亲和和 Job 级硬拓扑时，新增的候选可能排在更窄的原有候选之前，"落位不变"对它们不成立。这种组合没有验证。

用户报告的场景按这条规则走一遍。tier-2 的域 A、B、C 各有两个 tier-1 的域，每个 tier-1 域一个节点；A 已被匹配的 PodGroup 占用；作业有四个单 Pod 子组，每个子组要求落在一个 tier-1 域里，每个节点只放得下一个 Pod。

| 步骤 | 现行 | 本设计 |
| --- | --- | --- |
| 反亲和的含义 | 候选域只剩 B、C 和它们下面的四个 tier-1 域；B、C 的公共父域因为"跨了多个 tier-2 域"被去掉 | 可用域 = {B, C}。公共父域仍是候选，但只能用 B、C 下的节点 |
| Job 级尝试 | 四个 tier-1 域各放下 1 个子组，失败。B：放下 2 个，失败。C：放下 2 个，失败 | 由窄到宽：四个 tier-1 域各放下 1 个；B、C 各放下 2 个；公共父域 ∩ {B, C}：四个子组分别落在 B、C 下的四个节点，成功 |
| 结果 | `2/4 tasks in gang unschedulable` | 4/4。没有 Pod 落进 A |

这条规则是按约束的含义推出来的，不针对某个场景。按它可以预先判断：把上面的作业换成"没有 SubGroup 策略"，或者再加上"作业整体限定在 tier 3"，现行代码同样会失败。探测证实了这一点，包括已经为这个缺陷打过补丁的 dev-1.14（§5.3）。

同类系统的做法一致。Kueue、KAI、Koordinator、Kubernetes 的 workload 级调度和 Slurm 都是在节点一层屏蔽被排除的部分，父域保留为候选。其中 Kueue、Koordinator、Slurm 和 Kubernetes 的父域可用量随之变小；KAI 的容量预估仍按全部节点计算，是高估。调研没有找到把"部分被排除的父域"整个丢掉的系统 [调研-2]。

对插件的要求：gradient 回调的结果要能区分"这是一组容器"和"这是可用域"。不声明可用域的插件行为与现在完全相同，所以现有的和第三方的 gradient 插件不需要改。

这是一项语义变更。上游设计文档 `docs/design/group-topology-affinity.md` 现在写的是"比比较层更粗的候选跨了多个域，不是 required 条目的合法候选"。修订后的说法是：更粗的域作为容器合法，但只能使用其中未被排除的部分。

#### 4.2.3 资源必要条件

总量检查看不出碎片：两个各剩 4 核的节点加起来有 8 核，却放不下一个 8 核的 Pod。资源必要条件对候选域里的每个节点，按任务的规格算出最多还能放几个这样的 Pod，在域内求和，再与单元达到 gang 下限还需要的任务数比较。和小于需要数时，这个域一定放不下，不必试放。

- 它只用来排除。和够了不代表放得下，仍然要验证。
- 它在验证阶段、轮到某个候选时才计算，排在胜者之后的候选不会被计算。
- 被它跳过的候选要留下原因（"按资源最多放 k 个，需要 n 个"）。

#### 4.2.4 筛选的输出

每一层一个候选列表，加上每个被排除的域的原因：哪个插件、哪条约束，或者差多少资源。原因直接进入决策记录（§4.6）。

### 4.3 排序

#### 4.3.1 排序键

同一个单元的候选域按下面的键比较，前一个键相同才看后一个。

| 位次 | 键 | 方向 | 来源 | 依据 |
| --- | --- | --- | --- | --- |
| 1 | 域所在的层 | 窄的在前 | gradient 的分层 | 用户声明的拓扑意图 |
| 2 | 域分数 | 高的在前 | 各插件 `HyperNodeOrderFn` 分数之和 | 放进去之后最满的域优先，减少碎片；再叠加用户声明的偏好 |
| 3 | 本单元已在该域内的任务占比 | 高的在前 | 现行 NTA 的并列加分 | 同一个单元尽量待在一起 |
| 4 | 并列键 `hash(单元 UID, 域名, 轮次)` | 小的在前 | 新增 | 结果可重复；不同作业不会挤向同一个域；作业调度失败后，下一个周期换一种并列顺序 |

第 1、2 键就是上游的现行规则，只是从"试放之后比较"提前到"试放之前排序"。层的先后取自 gradient，本设计不重排：dev-1.14 对带 preferred SubGroup 条目的作业，Job 级的层序是"偏好的层、更宽的层、更窄的层"，新流程沿用它。这条路径没有被探测覆盖。第 3 键现在是分数里的一个加分项，建议改成独立的键（§4.3.4）。第 4 键替换现在的随机数。

#### 4.3.2 第一键：层

层严格优先于分数，两者不做加权。

- **依据是用户的声明。** 硬拓扑的含义是"尽量窄，最宽到某一层"。一个更满的 zone 不应当因为分数高而压过一个放得下的机架。
- **窄域优先也保护了大块资源。** 能放进机架的作业不去拆一个 zone，之后必须占用整个 zone 的作业才有地方放。按层级分配资源的系统都用这个规则：HiveD 从能满足请求的最低一级单元分配，只在必要时才拆上一级的单元 [HiveD]；Slurm 的树形拓扑选能满足请求的最低一级交换机 [调研-1]。

#### 4.3.3 第二键：分数

分数是各插件域分数之和，与现行相同。上游的评分项如下。

| 评分项 | 插件 | 公式 | 含义 |
| --- | --- | --- | --- |
| 装箱分 | network-topology-aware | 对单元请求了的、带权重的每种资源 r：`(已用 r + 单元请求 r) / 可分配 r`；按资源权重加权平均，再乘 100 和插件权重。任何一种资源放不下时记 0 | 把单元放进去之后，这个域有多满 |
| preferred 反亲和 | group-topology-affinity | `100 × 插件权重 × max(0, 1 − Σ 命中条目的权重 / 100)` | 候选域落在已被匹配 PodGroup 占用的域里时扣分 |

默认只有 CPU 和内存带权重，权重都是 1。dev-1.14 另有 SubGroup 的 preferred 亲和与反亲和两项，形式与第二行相同。

装箱分是决定名次的主要一项。它的排序效果是：**在放得下这个单元的同层域里，放进去之后占用比例最高的排最前。** 同层的域容量相同时，就是已经最满的排最前。

依据有三条。

- **减少碎片。** 把单元放进已经用了一部分的域，空着的域保持完整，之后的大作业才放得下。这对应装箱问题里"最佳适应"的思路：把物品放进装得下它的最满的箱子（域当作箱子，单元当作物品）。一维装箱里它用的箱子不超过最优解的 1.7 倍 [DS14]。生产系统的经验方向一致：Borg 指出把负载摊开的打分（它称为"最差适应"）会增加碎片，对需要大半台机器的大任务尤其不利，它最终采用以减少零散资源为目标的混合打分 [Borg]。详见 §6.2。
- **实测。** 同一批随机作业流，只改同层候选的先后，其余完全相同（§4.3.7 的表）。按分数排调度了 85.4% 的空闲容量；空的域优先是 71.2%；随机顺序是 77.5%。
- **与现行一致。** 现行在试放成功的候选里取这个分数的最大值。沿用它，结果才不变（§5.1）。

#### 4.3.4 第三键：已有任务占比

现行 NTA 在"装箱分最高且并列"的候选之间，按本单元已有任务落在该域的比例再加一次分。它的意图是让同一个单元的任务待在一起。

问题是这个加分只发给并列第一的候选，于是一个候选的分数取决于同批还有哪些候选，不满足 §4.3.5 的第二条。本设计建议把它改成独立的第三键：分数相同就比已有任务占比。意图不变，评分表变得可以预先计算。这是一处小的行为变更，只影响已经部分运行的子组；不批准时保留现行写法，代价是极少数并列情形下新旧流程的选择可能不同。

#### 4.3.5 评分表要满足的条件

排序发生在试放之前，所以每一项分数都必须满足：

1. **试放之前就能算。** 只读单元、候选域和试放之前的会话状态。
2. **只看这一个候选。** 不取决于同批还有哪些候选。
3. **确定。** 相同输入给出相同分数。

上面两个内置评分项满足这三条，唯一的例外是 §4.3.4 的并列加分，它不满足第 2 条。探测在没有触发并列加分的场景里直接验证了第 1、2 条：在运行 allocate 之前调用打分函数，事后选中的域就是事前分数最高的；一个域单独打分与和别的域一起打分，分数相同。第三方的 `HyperNodeOrderFn` 如果依赖试放留下的状态，或者依赖候选集合，需要调整；这无法逐一枚举。这是本设计对打分插件的唯一新要求；对 gradient 插件的要求见 §4.2.2。

#### 4.3.6 SubGroup 作业在 Job 级怎么排

带 SubGroup 策略的作业在 Job 级是个例外。现行规则下，Job 级候选域的分数是"各子组最终落在哪些子域，这些子域的分数之和"，要把整个作业试放完才知道。

本设计在 Job 级用同一张评分表、同一个排序键：把候选域当成整个作业的容器，分数取各子组对这个域本身的分数之和，排好之后取第一个验证通过的。当同层的域容量相同时，这等价于按"域本身有多满"排序。

它与现行规则的差别只在"同一层里有多个放得下的域时选哪一个"。实测（上游原型）：

| 度量 | 未修改的代码 | Job 级每个候选都试放（现行规则），子组级已排序 | Job 级先排序，取第一个通过的 |
| --- | --- | --- | --- |
| 1200 个单作业场景：中间一列能调度而本列调度不了 | — | — | 0 |
| 同上：与中间一列落位不同 | — | — | 684 个里 45 个（6.6%）：混合场景 459 个里 24 个，分母含没有 SubGroup 策略的作业；全部是 SubGroup 作业的争用场景 225 个里 21 个（9.3%）。所在的层相同：两种规则都逐层由窄到宽，只是层内的选择不同 |
| 200 个作业流（3760 个 SubGroup 作业）：调度的空闲容量 | 83.8% | 83.6% | 83.9%；与中间一列相比 42 个流更多，44 个流更少，114 个相同 |
| 同上：任务试放次数 | 206190 | 145876 | 83424 |
| 1024 节点、8 个 SubGroup 作业的 allocate 耗时（第一轮原型测得） | 1.51 s | 1.37 s | 0.041 s |

按作业流累计，三种做法调度的容量没有可见差别。随机作业流里，Job 级排序的任务试放次数比中间一列少 43%，比未修改的代码少 60%；1024 节点的基准上耗时差一个量级。因此建议在 Job 级也采用排序。它改变一部分作业的落位，需要单独批准，并排在其他步骤之后上线（§8）。不批准时，Job 级保留"每个候选都试放"，子组级仍然排序；这样 Job 级的成本和 §2.3 的重放问题对 SubGroup 作业依然存在。

原型的限制：原型在 Job 级排序后仍然撤销并重放胜者。设计要求保留胜者的试放结果，这一点对 SubGroup 作业还没有实现，也没有用 DRA 场景验证。

#### 4.3.7 为什么不把"最容易放下的"排在前面

把最空的域排在最前，试放几乎总是一次成功，看起来最省。同一批作业流的实测：

| 同层候选的先后 | 调度的空闲容量 | 排第一的候选直接通过 | 每次决策的试放次数 |
| --- | --- | --- | --- |
| 分数从高到低（本设计） | 85.4% | 87.7% | 1.20 |
| 最空的在前 | 71.2% | 98.2% | 1.03 |
| 按名字 | 82.6% | 61.3% | 2.64 |
| 伪随机 | 77.5% | 80.5% | 1.66 |

最空优先每次决策省 0.17 次试放，代价是少调度 14 个百分点的容量。排序的依据是放置质量；省试放的事交给资源必要条件去做。按名字排的容量接近按分数排，因为它总是先用名字靠前的域，客观上也在装箱，但每次决策要多试放一倍以上，而且固定偏向某些域。

#### 4.3.8 并列键

分数和第三键都相同的候选，按 `hash(单元 UID, 域名, 轮次)` 从小到大排。同一个键也用于域内并列的节点。

"轮次"是这个作业连续调度失败的周期数，第一次尝试时为 0。四种选择的比较：

| 并列时的规则 | 相同输入的结果 | 不同作业之间 | 作业的成功取决于并列怎么选时 |
| --- | --- | --- | --- |
| 随机（现行） | 每次不同，无法复现 | 分散 | 每个周期换一种选法，几个周期内成功 |
| 域名 | 相同 | 所有作业都选名字最靠前的域 | 选错了就永远选错 |
| `hash(单元 UID, 域名)` | 相同 | 分散：每个作业有自己固定的顺序 | 选错了就永远选错 |
| `hash(单元 UID, 域名, 轮次)` | 相同（轮次是输入的一部分，写进决策记录） | 分散 | 每失败一个周期换一种选法 |

最后一列是独立评审发现的问题（§10.1）。现行的随机并列有一个没有写明的作用：一个作业如果只有在并列选对时才放得下，随机相当于每个周期重试一种选法。把并列固定下来会去掉这个作用。实测（16 个作业，每个最多 12 个调度周期，两类场景：子组之间并列、域内节点并列）：

| 并列时的规则 | 第一个周期调度成功 | 12 个周期内调度成功 | 始终调度不了 |
| --- | --- | --- | --- |
| 随机（现行） | 每次运行不同，观察到 4–13 个 | 16 | 0 |
| 哈希，不带轮次 | 8 | 8 | 8 |
| 哈希，带轮次 | 8 | 16（最长 9 个周期） | 0 |

另外的实测：4 个相同的机架、40 次会话只产生一种落位；20 个单 Pod 作业落在 8 个相同的节点上，每个节点 2–3 个。

并列键只在分数完全相同时起作用。一旦某个域被用了一点，它的装箱分就更高，后面的作业会按分数继续往里放，不会因为哈希而摊开。

用哈希做并列键没有文献依据，主流调度器在并列时随机选 [K8s-Sched]。这是工程取舍：结果要可复现，又不能让所有作业偏向同一个域，也不能丢掉随机并列隐含的重试。

#### 4.3.9 可选的排序项：节点偏好

现行的选域不看节点级的偏好。Pod 带 preferred NodeAffinity、被偏好的节点全在机架 r01 时，40 次会话里只有 6 次选中 r01（一次运行的结果，每次运行不同）。

可以增加一个评分项：取一个代表任务，对所有候选域的节点统一打一次分，每个域取最好的 k 个节点的平均（k 是待放的任务数），乘权重后加进域分数。所有候选共用一次打分，所以满足 §4.3.5。默认权重为 0，即不启用；启用是行为变更。

#### 4.3.10 同类系统的排序方式

排序键的前三个位次都能在同类系统里找到对应的做法。第 4 键只有"并列时用确定的规则"这一点有先例（按名字或 ID）；带轮次的哈希没有先例。下表来自对各系统固定版本源码和文档的调研 [调研-1]。

| 系统 | 候选域的先后 | 并列 |
| --- | --- | --- |
| Koordinator v1.8.0 | 已有本作业 Pod 多的在前；能提供的空位少的在前（装箱）；分数；名字 | 确定 |
| KAI v0.19.0 | 层优先；同一父域内按资源比例从高到低；ID | 确定 |
| Kueue TAS v0.20.5 | BestFit：可容纳的份数多的在前，其次可容纳的 Pod 数少的在前，再按域标签值 | 确定 |
| Slurm `topology/tree` | 能满足请求的最低一级交换机；其下按最佳适应 | — |
| Kubernetes workload 级调度（master） | 候选放置打分取最高 | 随机 |
| Volcano 现行（上游） | 层优先；`HyperNodeOrderFn` 分数最高 | 随机 |

Koordinator 的顺序与 §4.3.1 的第 3、2、4 键几乎相同。Kueue、KAI、Koordinator 和 Slurm 都是先排序，不对每个候选做完整试放。KAI 与本设计最接近：排好之后逐个用真实流程放置，第一个成功就返回。Kueue 只排序、不验证，所以在它的估算与 kube-scheduler 不一致时作业会卡在 Pending；本设计保留验证，就是为了避免这一点。

### 4.4 验证

验证用的是现有的逐任务流程（`allocateResourcesForTasks`），不改动：对候选域里可用的节点，逐个任务运行 PrePredicate、Predicate、节点打分，选出节点后 `Statement.Allocate`；全部放完检查 gang 条件。因此谓词、节点打分、队列与配额、设备类插件看到的调用与现在相同，只是次数变少。

与现行的三处不同：

- **第一个通过的候选就是结果。** 排在它后面的候选不再试放，在决策记录里标为"未评估"。
- **胜者不撤销、不重放。** 试放得到的 Statement 直接作为结果保留。胜者的每个任务只触发一次 Allocate 事件，没有 Deallocate。排在胜者之前、放下一部分任务后失败的候选仍然产生 Allocate 和 Deallocate，与现行相同。有状态的插件（例如 DRA）读到的就是胜者这一次试放留下的状态，§2.3 的重放问题在排序路径上不再出现。SubGroup 作业的 Job 级见 §4.3.6。
- **失败的候选留下原因。** 撤销之后记下第一个放不下的任务和它的节点级原因。

一层的候选全部失败时进入更宽的一层，与现行相同。

与上游"不可调度作业缓存"（Alpha，默认关闭）的关系：这个缓存按"每个仍然可达的候选为什么拒绝了作业"来决定何时重新调度它。提前停止会让这些记录变少。规则是：缓存打开时，只要发生过提前停止而作业在会话结束时仍有任务没调度，就给它写一条不可缓存的标记；被资源必要条件跳过的候选写一条资源类的拒绝记录。这样不会漏掉唤醒，代价是这类作业不被缓存。

### 4.5 找不到解时的有限重试

正常搜索不变。只有它在所有层都找不到解时，才进入重试。

- **重试什么。** 正常搜索里出现过"已经放下一部分子组，之后有子组放不下"的候选域。这种候选域里的失败可能是顺序造成的。
- **怎么重试。** 在同一个候选域里，把放不下的子组提到最前面，其余顺序不变，把整个作业重新试放一遍。还有放不下的就继续提前，直到出现重复的顺序。
- **预算。** 每个作业每个调度周期最多重试 N 次，建议默认 4 次。
- **顺序。** 从最窄的层开始，但留 1 次给最后一个候选域。它通常是最宽的，可用的节点最多，成功的机会最大；先试窄的是为了让结果的层尽量窄。
- **不做重复的搜索。** 可用节点完全相同的两个候选域只重试一个。被提前的子组在空的候选域里也放不下时，立即放弃这个候选域，这次尝试不计入预算。
- **门槛。** 对要求全部任务都放下的作业：候选域里可用的空闲资源总量小于待放任务的请求总量时，直接跳过，不消耗预算。
- **失败不留痕迹。** 重试全部失败后，作业的失败原因和各任务的状态恢复成正常搜索结束时的样子。用户看到的不可调度信息与不开重试时相同。
- **如实上报。** 预算用完时，记录"搜索未完成"以及还有几个候选域没有重试。

每次重试都是一次普通的 Job 级试放，调用的插件回调与现行的试放完全相同，不需要插件提供新的能力。重试成功时同样保留这次试放，不重放。

用 §2.3 的例子：子组 X 先放，占掉机架 a；子组 Y 放不下，作业失败。重试时 Y 提前，落在 a；X 随后落在 b；作业 2/2。

这个做法就是"哪里失败就先安排哪里"：贪心地构造一个方案，找出造成失败的元素，把它们提前，再构造一次 [SWO]。它不保证找到所有的解，所以预算和"搜索未完成"的上报是设计的一部分。实测里，预算 4 次时子组互相挡路造成的漏解从 20 个降到 1 个（410 个可行场景）；预算足够大时降到 0。

可选的增强，默认不启用：现行搜索在某一层全部失败后直接去更宽的一层。可以先在这一层重试，成功就不必去更宽的层。它能让更多作业落在更窄的层（层比必要的宽的作业从 12 个降到 2 个），但会改变现在能调度的作业的落位（1200 个场景里 17 个），成功路径的试放次数增加约 4%。它需要自己的预算：与最后的重试共用预算时，预算小的情况下反而少调度作业。

### 4.6 决策记录

每次"排序 + 验证"产出一条记录。它是流程本身的副产品，不是事后重算的。下面是原型在"排名第一的机架带污点"场景里的输出，为便于阅读改成每个候选一行，并省略了最后两个未评估的候选。

```text
job c1/job layer 0:
  #1 z0-r04 (tier 1) score=100.00 failedVerify [job-p00: In hyperNode z0-r04: 0/4 nodes are unavailable: 4 node(s) had untolerated taint(s).]
  #2 z0-r03 (tier 1) score=87.50  selected
  #3 z0-r02 (tier 1) score=75.00  notEvaluated
  #4 z0-r01 (tier 1) score=62.50  notEvaluated
```

每个候选恰好有一个结论：选中、验证失败（带原因）、被资源必要条件跳过（带数字）、未评估。排在胜者之前的都已评估，排在之后的都未评估。原型的随机测试对每条记录都检查了这些不变量。

另有三类记录。前两行是原型的输出，第三行是设计中的格式，原型只记下了作业名。

```text
usable region of c1/pg-myq: [z1 z2]                               # 可用域（z1、z2 即文中的 B、C）；正式实现还要列出被排除的域和原因
job c1/job in z0: retry 1 with [c1/job/worker-1] first succeeded   # 重试：在哪个域、把谁提前、结果
job c1/job: search incomplete, retry budget 4 used, 2 blocked domains not retried   # 预算用完
```

输出位置：

| 情形 | 内容 | 位置 |
| --- | --- | --- |
| 不可调度 | 各结论的计数，加一个按稳定规则选出的失败原因；可用域与被排除的域；搜索是否完成 | 现有的 PodGroup 条件消息 |
| 已调度 | 胜者、名次、各评分项，以及排在它前面的候选的失败原因 | 日志 |
| 统计 | 每个作业的候选数、试放次数、跳过数、胜者名次、重试次数 | 指标 |

三条约束：

- 完整的排名表不写进 Event 或条件消息。Koordinator 曾因逐域明细超过事件长度上限而改为只报汇总 [调研-1]。
- 不可调度消息里的那个失败原因按域名稳定选取，不取"排名最后的候选"。否则占用率一变消息就变，会增加 PodGroup 状态的写入。
- 不可调度消息说的是"没有找到"，并附上搜索覆盖了什么。本设计的搜索不完备（§6.3），所以消息不写"不存在可行的放置"。唯一的例外是每个候选都被筛选或资源必要条件排除，这时原因本身就是证明。

## 5. 为什么有效

### 5.1 选出的域与现行相同

设某一层筛选后的候选集合为 C，其中试放能成功的子集为 F，候选 c 的分数为 s(c)。

- 现行：把 C 里每个候选都试放，在 F 里取 s 最大的。
- 本设计：把 C 按 s 从高到低排好，逐个试放，取第一个成功的。它就是 F 里 s 最大的那个。

两者相同，需要四个前提：

1. s(c) 在试放前后相同，并且不取决于 F。这就是 §4.3.5 对评分表的要求。
2. 对 c 的试放结果不取决于之前试放过并撤销的候选。这是一条假设：它要求撤销把后续试放会读到的状态都恢复原样。
3. 并列按同一规则裁决。现行的并列是随机的，所以对照组取"现行 + 固定并列"。
4. 资源必要条件只跳过试放一定失败的候选（§4.2.3）。

已知不满足前提的地方有四处：

- 前提 1：NTA 的并列加分（§4.3.4）；SubGroup 作业的 Job 级分数（§4.3.6）。
- 前提 2：域内节点超过 100 个时启用的节点抽样，它的游标会被试放次数推进（§10.2）。
- 前提 2：撤销不恢复每个任务的插件调度状态（例如 DRA 的）。下一次试放会重写它，所以不重放胜者就不受影响；这一点只在 §2.3 的 DRA 场景上验证过。

"选出的域相同"之外，"逐 Pod 落位相同"还要求域内不触发节点抽样。下面的测试比较的是 Pod 到节点的映射，没有比较会话的其他终态；§9.1 要求把比较范围扩大。

实测：

| 测试 | 规模 | 与"现行 + 固定并列"相比 |
| --- | --- | --- |
| 随机会话：1–3 个 zone，硬拓扑、SubGroup、部分运行、soft 拓扑作业混合，1–4 个作业 | 700 个会话 | 逐 Pod 落位不同的会话：0 |
| 单作业场景：反亲和、作业硬拓扑、两到三种 SubGroup 策略、nodeSelector 随机组合；每个落位再由独立程序按声明的约束检查合法性 | 2800 次场景运行，约 2200 个不同的场景（其中两组用同一个生成器，约 600 个重叠） | 现行能调度而新流程调度不了：0；落位不同：0；非法落位：0 |
| 现有的调度器单元测试全集，强制走新路径 | 上游 58 个包；dev-1.14 46 个包 | 见 §5.6 |

### 5.2 更快

记 T 为任务数，F 为首个有解层里放得下的候选数，X 为排在胜者之前、验证失败的候选数。

| 路径 | 现行 | 本设计 |
| --- | --- | --- |
| 成功 | 试放 F 次，重放 1 次；Allocate 事件 2·T·F+T | 试放 1+X 次，不重放；胜者的 Allocate 事件为 T |
| 全部失败 | 每个候选试放到第一个放不下的任务 | 相同；资源必要条件跳过它能证明的部分 |
| 额外开销 | — | 每层打一次分；资源必要条件对轮到的候选是 O(域内节点数) |

X 有多大取决于排第一的候选能不能通过。实测：

| 负载 | 每次决策的候选数 | 排第一的候选直接通过 | 每次决策的试放次数 |
| --- | --- | --- | --- |
| 400 个混合随机会话 | 1.9 | 95.2% | 1.06 |
| 300 个偏紧的作业流（需求是空闲容量的 1.2 倍） | 5.9 | 87.7% | 1.20 |

成功路径上的事件数（一个 4 任务的硬拓扑作业，R 个相同的空机架）：

| 机架数 R | 谓词调用（现行 → 本设计） | Allocate 事件 | Deallocate 事件 |
| --- | --- | --- | --- |
| 1 | 10 → 10 | 12 → 4 | 8 → 0 |
| 4 | 40 → 10 | 36 → 4 | 32 → 0 |
| 16 | 160 → 10 | 132 → 4 | 128 → 0 |
| 32 | 320 → 10 | 260 → 4 | 256 → 0 |

1024 节点的基准（4 个 zone × 16 个机架 × 16 个节点，只计 allocate 的执行时间，全部作业都放得下；在第一轮原型上测得）：

| 场景 | 现行 | 本设计 |
| --- | --- | --- |
| 20 个硬拓扑作业 × 8 个 Pod | 2.00 s | 0.046 s |
| 8 个 SubGroup 作业 × 16 个 Pod，Job 级保留"每个候选都试放" | 1.51 s | 1.37 s |
| 同上，Job 级也排序（§4.3.6） | 1.51 s | 0.041 s |

失败路径上排序没有帮助。上面的作业流里，没有胜者的层有 4271 个，共试放 24462 次；资源必要条件把它降到 22312 次。在一个全部碎片化的 16 机架例子里，它把 16 次试放降到 0 次。由谓词造成的失败本设计不改善。

基准是合成负载。生产上成功路径和失败路径各占多少，决定实际收益；这个比例目前未知。

### 5.3 不丢可调度性，并且少漏解

每个机制为什么不会让"能调度"变成"调度不了"：

| 机制 | 它对搜索做了什么 | 为什么不丢 |
| --- | --- | --- |
| 排序与提前停止 | 候选集合不变，每个候选的验证方式不变，只改先后 | 只在已经有候选通过时才停。全部失败时每个候选仍然被验证过。前提是试放结果与候选的先后无关（§5.1 的前提 2） |
| 资源必要条件 | 跳过一部分候选 | 只跳过按资源算一定放不下的 |
| 可用域 | 候选只增不减 | 原有的候选全部落在可用域内，节点不变、先后不变；新增的候选排在所有原有候选之后。这依赖对可用域提供方的要求，并且有一个已知的例外（§4.2.2） |
| 有限重试 | 增加试放 | 只在正常搜索找不到解之后才运行 |

所以这四个机制叠加之后，现行能调度的作业走的仍是原来那条路，得到原来的落位；变化只发生在现行调度不了的作业上。

用户报告的缺陷和它的变体（"是"表示存在合法放置；数字是放下的 Pod 数）：

| 场景 | 存在合法放置 | 上游现行 | dev-1.14 现行 | 本设计（两条基线） |
| --- | --- | --- | --- | --- |
| 用户报告的场景：反亲和在 tier 2，四个单 Pod 子组各限 tier 1 | 是 | 0/4 | 4/4 | 4/4 |
| 反亲和在 tier 2，没有 SubGroup 策略 | 是 | 0/4 | 0/4 | 4/4 |
| 作业限 tier 3，反亲和在 tier 2，子组同第一行 | 是 | 0/4 | 0/4 | 4/4 |
| 作业限 tier 3，反亲和在 tier 2，没有 SubGroup 策略 | 是 | 0/4 | 0/4 | 4/4 |
| 反亲和在 tier 2，两个 2-Pod 子组各限 tier 2 | 是 | 0/4 | 4/4 | 4/4 |
| 作业 soft tier 2，反亲和在 tier 2，子组同第一行 | 是 | 0/4 | 4/4 | 4/4 |
| 对照：2 个 Pod，一个域就够 | 是 | 2/2 | 2/2 | 2/2 |
| 对照：作业限 tier 2 加反亲和，4 个 Pod 必须跨两个 tier-2 域 | 否 | 0/4 | 0/4 | 0/4 |

与暴力求解器对照（上游原型；求解器不调用调度器代码，对小场景穷举"是否存在合法放置"和"最窄能放在哪一层"；重试按 §4.5 的顺序）：

| 配置 | 1200 个混合场景，982 个可行：调度不了的 | 1000 个子组争用场景，410 个可行：调度不了的 | 现行能调度而丢失的 | 落位不同的 |
| --- | --- | --- | --- | --- |
| 现行 | 39 | 20 | — | — |
| 排序 + 验证 | 39 | 20 | 0 | 0 |
| 加可用域 | 25 | 20 | 0 | 0 |
| 再加重试，预算 2 | 5 | 2 | 0 | 0 |
| 再加重试，预算 4 | 4 | 1 | 0 | 0 |
| 再加重试，预算 8 | 4 | 1 | 0 | 0 |

争用场景不含反亲和，可用域对它不起作用；该列"预算 2"一格取自不开可用域的配置。

调度器放下了而求解器判定无解的情况出现 0 次。混合场景里最后剩下的 4 个都是域内任务大小不一造成的（§2.3 的第三类），不在本设计范围内。争用场景里剩下的 1 个在预算 64 时消失。

39 个里至少有 14 个只有在可用域语义下才是合法放置（§4.2.2），即单靠可用域找回的那部分。按上游设计文档现在的表述，更粗的域不是合法候选，所以这部分取决于是否接受新语义，而不是现行搜索漏掉的。靠重试找回的 21 个里可能也有这样的场景，没有单独统计。

边界：上面的保证是对单个作业、同样的会话状态说的。一个作业新变成可调度后会占用资源和域，同一个调度周期里排在后面的作业可能因此放不下。600 个多作业会话（1496 个待调度作业）的实测：多调度 29 个作业；没有任何一个会话调度成功的作业数减少；有 7 个会话是一个作业新调度成功、另一个作业落空。另一种情形是两个互相 required 反亲和的作业，见 §10.2。

### 5.4 过程可以复述

- 流程本身两句话说得完：先筛掉不可能的；剩下的按公开的表排好，从头逐个试，第一个放得下的就是结果。
- 相同输入得到相同结果。并列键的轮次是输入的一部分，写在决策记录里。前提是域内节点数不触发节点抽样，并且只对 allocate 成立；抢占和回填仍然用随机数。
- 每个候选在决策记录里恰好有一个结论，结论带原因。"为什么选了它"的回答是"它排在第 k 位，前 k−1 个分别因为什么没通过"。"为什么调度不了"的回答按候选域逐个给出，而不是只给一个域的原因。

### 5.5 现有插件不需要改

| 接触点 | 本设计下的行为 |
| --- | --- |
| 谓词、PrePredicate、队列节点过滤、节点打分 | 调用方式不变，只在被验证的候选里运行 |
| 事件回调（proportion、capacity、drf、NTA、predicates 等） | 胜者的每个任务一次 Allocate，不再有撤销与重放。排在胜者之前、验证失败的候选与现行一样产生 Allocate 和 Deallocate |
| 需要 Reserve 状态的插件（DRA） | 胜者不重放，读到的是它自己试放时建立的状态 |
| `HyperNodeOrderFn` | 调用时机从试放之后提前到试放之前；需要满足 §4.3.5 |
| gradient 回调 | 不声明可用域的插件行为不变 |

### 5.6 现有单元测试在新路径下的结果

用开关把 allocate 强制切到新路径，运行 `go test ./pkg/scheduler/...`。结果来自最终的原型。

| 基线 | 开关全关 | 排序 + 资源必要条件 | 再加重试（预算 4） | 再加可用域 |
| --- | --- | --- | --- | --- |
| 上游，58 个包 | 全部通过 | 全部通过 | 全部通过 | 57 个通过，1 个用例失败 |
| dev-1.14，46 个包 | 全部通过 | 45 个通过，1 个用例失败 | 未单独运行 | 森林优先：全部通过；替换森林：全部通过 |

- 上游的每份日志开头记录了当次运行的环境变量；另有一次"可用域 + 重试、Job 级每个候选都试放"的运行，结果与最后一列相同。dev-1.14 的日志没有记录环境变量，开关组合见文件名。
- 上游失败的用例是 `TestNominationFastPathMatchesPluginGradients`。它断言"提名快速路径"与完整的 gradient 等价，而原型只改了后者。两者需要一起改（§7）。
- dev-1.14 失败的用例是 `TestAllocateWithPVC/static_pv_matched_and_node_with_enough_resources`。它在未修改的代码上同样间歇失败：整个包重跑 8 次有 3 次失败，其中 2 次确认是这个用例，另 1 次没有记下用例名。作业不带拓扑，不经过 HyperNode 路径；排序开关打开时，节点级的并列键对它生效。同一批运行里，开关更多的两种配置都没有出现这个失败。
- dev-1.14 上"可用域全部通过"对候选森林不构成证据：森林的单元测试用的是不声明可用域的假插件，森林路径照常启用。
- 探测本身在 dev-1.14 上有一个按设计失败的用例：`TestProto2R3SingleJobMonotonic` 断言落位不变，而直接用可用域替换森林会改变 26 个作业的落位（§10.3 第 6 项）。森林优先的对应用例 `TestProto2R3fForestFirstMonotonic` 通过。

## 6. 局部最优、全局最优与调度效率

### 6.1 一次放置里的四层决定

"全局最优"指同时考虑所有作业、所有子组、所有任务，让某个总目标最大。一次放置实际上由四层决定叠成，本设计在每一层的做法不同。

| 决定 | 本设计的做法 | 性质 |
| --- | --- | --- |
| 一个单元选哪个域 | 按评分表排序，取第一个通过验证的 | 在给定的评分表下是精确的：选到的就是分数最高的可行域 |
| 作业里各子组的先后 | 固定顺序，前面的放下之后不回头；找不到解时有限重试 | 贪心，失败后补救 |
| 域内每个任务选哪个节点 | 逐任务取分数最高的节点。现有流程，不改 | 贪心 |
| 多个作业之间 | 按队列和优先级依次放置。现有流程，不改 | 贪心；评分表里的装箱分为后来的作业留出整块资源 |

本设计保证第一行，对第二行做有限的补救，第三、四行维持现状。下面先看文献对这种取舍的说法，再给出本设计在每一层付出的代价。

### 6.2 文献的依据

文献核查由独立的调研子代理完成，每条都对照了一手来源；原始报告和引句见附录 A 的"调研"。下面只列与设计选择直接相关的结论，并保留不利于本设计的证据。

**第一，精确的全局最优在计算上不现实，在线调度器都不这么做。**

- 装箱问题是 NP 难的；除非 P = NP，不存在近似比好于 3/2 的多项式算法 [WS11]。资源多于一种时，除非 P = NP，连渐近的多项式近似方案都不存在 [BCS09，转述 Woeginger 1997]。Tetris 把多资源集群调度建模成多维装箱，用启发式打分求解 [Tetris]。
- kube-scheduler 和 Borg 都是两步：先检查可行，再打分取最高 [K8s-Sched][Borg]。它们还主动少看候选来换时延。kube-scheduler 默认只找到一部分可行节点就开始打分，这个比例随集群规模下降，5000 节点时是 10%，下限 5%；文档说明比例低会带来不够理想的放置 [K8s-Perf]。Borg 按随机顺序检查机器，找到"足够多"的可行机器就开始打分；加上打分缓存和等价类，从零调度一个 cell 的负载通常用几百秒，关掉这些技术后三天没有跑完 [Borg]。
- Kubernetes 新的 workload 级调度对一组 Pod 生成候选放置、检查可行、打分，PodGroup 内的 Pod 按顺序处理，设计文档写明"避免复杂的回溯" [KEP-5732]。

三段流程与这些系统同构。差别在提前停止的条件：它们在"找到足够多的可行候选"时停，可能错过分数更高的；本设计先给全部候选打分（打分不需要试放），只在"按分数排好之后的第一个可行候选"处停，不会错过分数更高的可行候选。

**第二，贪心加上合适的先后有可以证明的界，但只在简化的问题上。**

- §4.3.3 的排序规则对应装箱里的"最佳适应"：把物品放进装得下它的最满的箱子。这个对应是本文的类比（域当作箱子，单元当作物品），没有见到论文这样表述。一维装箱里，最佳适应用的箱子数不超过最优解的 1.7 倍（向下取整）[DS14]；按固定顺序找第一个装得下的箱子（"首次适应"）有同样的界 [DS13]。这是最坏情况的界，只对单一资源成立；多种资源加拓扑约束时没有对应的结论。所以它是方向上的依据，不是对本设计的保证。§4.3.7 的实测与它一致：按名字排（即首次适应）的容量接近按分数排，最空优先（"最差适应"）明显更差。
- 先放大的物品（"首次适应递减"），一维装箱的界收紧到 11/9·OPT + 6/9 [Dósa07，经 DS13 转述]。排序的对象是物品，对应到本设计是"先放哪个子组、哪个任务"，不是域的先后。约束满足领域有同样的经验，称为先失败原则："要想成功，先试最可能失败的地方" [HE80]；原文讨论的是回溯搜索的开销，不是方案的质量。Medea 的启发式之一就是先放候选节点最少的容器 [Medea]。§4.5 把放不下的子组提前，用的是同一个思路。
- 在层级拓扑里从低层往高层分配是 HiveD 的做法：先找能满足请求的最低一级空闲单元，没有才逐级向上，目的是"尽可能多地保留高层单元" [HiveD]。§4.3.2 与它一致。
- 分数怎么算，生产系统的经验是：把负载摊开的打分增加碎片，对需要大半台机器的大任务尤其不利；装得最紧的打分对资源估计误差敏感；Borg 最后用的是以减少零散资源为目标的混合打分，装箱效率比纯粹的最佳适应高 3%–5% [Borg]。对 GPU 共享负载，专门针对碎片设计的打分比通用的最佳适应更好 [FGD]。

最后一点说明评分表可以继续改进。本设计不规定分数怎么算，只规定分数必须在试放之前可得（§4.3.5）。更好的打分可以作为插件的评分项加进来，流程不变。

**第三，全局优化器存在。它们换来更好的放置，代价是时延、复杂度，以及对约束形式的限制。**

- Quincy 和 Firmament 把调度写成最小费用流，在它们的费用模型内给出全局最优的分配 [Quincy][Firmament]。Quincy 报告它明显好于贪心：跨集群的数据传输最多减少到 1/3.9，吞吐最多提高 40%；它也说明 gang 调度不适用于它的场景。Firmament 复现 Quincy 的求解器，在 12,500 台机器上中位耗时 64 秒，要靠两种算法并行和增量求解才降到亚秒级；提前终止求解器会错放数千个任务。
- Medea 用整数线性规划处理长期运行应用的放置约束。它的求解器在 90% 利用率下也几乎没有约束违反，而它自己的启发式算法在低利用率下就有 10%–20% 的违反。它只把求解器用在长期运行的应用上，每 10 秒一轮，5000 台机器平均 850 毫秒；其余任务走另一个调度器，"保证基于任务的应用的调度时延不受影响" [Medea]。
- TetriSched 用混合整数线性规划做全局重排，全局调度对 SLO 达成率的贡献最高 36%。同一篇论文也写明，全局调度的时延过高时，贪心策略是可行的选择 [TetriSched]。

这些结果说明两件事。全局优化确实能得到更好的放置，这是本设计放弃的东西，§6.3 给出放弃了多少。代价也写在同一批论文里：Firmament 靠增量求解和两种算法并行才把时延降下来，Medea 把求解器放在对时延不敏感的路径上；它们都要求约束能写成求解器的模型。Volcano 的硬约束由任意插件的谓词给出，不能预先写成流网络或线性约束；这是验证必须使用真实逐任务流程的原因，也是本设计不引入求解器的原因。

**第四，贪心失败之后的补救：便宜的办法先试，失败了才升级。**

- 有限差异搜索的出发点是一个直觉：好的启发式失败时，往往只是途中走错了少数几步 [LDS]。作者说明这是直觉；只有把允许偏离的次数放开到整棵搜索树，才保证有解必能找到。
- "吱呀作响的轮子"优化：贪心地构造一个方案，找出造成问题的元素，提高它们的优先级，让下一轮先处理它们。论文说明它可能陷入小的循环 [SWO]。
- 失败才升级有生产先例。kube-scheduler 的抢占阶段只在没有可行节点时运行 [K8s-Framework]。微软的 Philly 在一个调度请求重试固定次数之后放宽它的局部性约束 [Philly]。

§4.5 的重试是这一类做法里最简单的一种：只在失败后运行，只调整先后，有预算，预算用完如实上报。它与"提前终止求解器"不同：每次重试都是一次完整的真实试放，结果要么合法并被采用，要么被丢弃，不会留下半成品。

**不利于本设计的证据。**

- 窄的层不是对所有作业都值得等。Tiresias 观察到，强制把分布式训练作业集中放置，会让作业在集群别处有足够空闲时仍然排队，造成更长的等待和更低的利用率；只有一部分模型对放置敏感 [Tiresias]。在 Volcano 里这由用户决定：硬拓扑是用户提出的要求，soft 拓扑的作业不会因为放不进窄的域而等待。本设计的排序键只决定先试谁。
- 最满优先不是唯一合理的方向。Philly 给机架排序用的是"已分配量从低到高"，即最空的在前；同一篇论文也报告，5–8 块 GPU 的作业有 74.2% 的排队时延来自碎片 [Philly]。装箱分的方向和权重本来就是插件的配置；本设计沿用现行方向。
- 没有找到论文度量过"逐个候选的贪心加窄层优先"在 gang 和拓扑约束下距最优有多远。§6.3 的数字是本设计自己量的，规模小，是合成负载。
- 并列键用哈希没有文献依据。主流调度器在并列时随机选 [K8s-Sched]。用哈希是工程取舍，理由和代价见 §4.3.8。

### 6.3 本设计在每一层放弃了什么

| 决定 | 放弃的东西 | 实测的代价 | 可以再加强的地方 |
| --- | --- | --- | --- |
| 单元选域 | 不为后面的作业预留位置，只靠装箱分间接照顾 | 300 个作业流：调度了空闲容量的 85.4%。事后从 25 种顺序里挑最好的一种是 87.1%，相差 1.7 个百分点 | 更好的评分项，以插件形式加入 |
| 子组的先后 | 不回溯 | 重试预算 4：982 个可行场景漏 4 个，全部属于下面"任务选节点"一行；410 个子组争用场景漏 1 个 | 调大预算。预算 64 时争用场景漏 0 个 |
| 层 | 一层全部失败就去更宽的层，不在本层调整先后 | 479 个带作业级硬拓扑的可行场景里，12 个落在比必要更宽的层 | 换层之前先重试（§4.5 的可选项），降到 2 个 |
| 任务选节点 | 不处理 | 982 个可行场景漏 4 个 | 域内先放大的任务。未做原型 |
| 多个作业之间 | 不处理 | 600 个多作业会话里，7 个会话出现一个作业新调度成功、另一个落空；没有会话的成功作业数减少 | — |

关于"事后最好"：它是设计的顺序加 24 种伪随机顺序里结果最好的一种，不是最优解，真正的最优可能更高。设计的顺序在 99 个流里好于全部 24 种随机顺序，在 107 个流里被某一种随机顺序超过。

### 6.4 没有采用的做法

| 做法 | 能得到什么 | 不采用的原因 |
| --- | --- | --- |
| 子组之间的联合回溯 | 子组互相挡路的全部情形 | 要求每个插件支持精确撤销；过程无法复述；最坏情况下搜索量是指数级 |
| 最小费用流、整数规划 | 给定模型内的全局最优 | 插件的谓词无法写成模型；时延高；提前终止不安全 [Firmament] |
| 只看一部分候选，或对候选采样 | 更低的时延 | 可能错过唯一可行的候选，让能调度的作业调度不了，违反 G1。本设计只在已经有候选通过时才停 |
| 把最容易放下的域排在前面 | 试放几乎总是一次成功 | 少调度 14 个百分点的容量（§4.3.7） |
| 层与分数加权混合 | 一个总分 | 更满的宽域会压过放得下的窄域，违背用户声明的拓扑意图 |

## 7. 需要一起改的地方

三段流程只改 allocate 的搜索方式。可用域语义还牵涉到下面这些地方，它们必须和它保持一致。

| 接触点 | 现状 | 本设计的要求 | 原型状态 |
| --- | --- | --- | --- |
| 总量检查 | 按域的全部节点求和 | 按域里可用的节点求和。否则被部分排除的域会带着不能用的资源通过检查，每个周期白白试放 | 已实现 |
| 域分数 | 按域的全部节点计算 | 被部分排除的域按可用部分计算 | 未实现 |
| 作业和子组的落位记录（`AllocatedHyperNode` 与对应注解） | 记选中的候选域的名字 | 记实际落位的最近公共祖先。调度器内部的虚拟根名不写入注解 | 未实现。dev-1.14 的候选森林路径已经这样做 |
| 不可调度的摘要 | 每层"可用 k/n" | 区分整体可用、部分可用、被排除三种。否则同一个父域会既算可用又算被排除 | 未实现 |
| 上游的提名快速路径 | 另一份按名字求交的合法性判断，单测断言它与完整判断等价 | 提名合法 = 提名域落在某个容器里，并且它的节点都在可用域内。单测的参照随之改写 | 未改。实测是安全的：480 种组合里没有一次接受含被排除节点的提名。有 80 处与单测的参照不一致：72 处是参照的问题（它按容器的全部节点判断，包含了被排除的节点），8 处是快速路径更严（提名域在可用域内，但只有被部分排除的父域能当它的容器）。行为分析子代理在第二轮原型上测得，没有重跑 |
| 抢占、回收使用的候选 | 按名字求交 | 同样按"容器 ∩ 可用域"。否则跨域的放置只能在资源空闲时成立，抢占路径给不出提名 | 未改 |
| 上游的不可调度作业缓存 | 依赖拒绝记录 | §4.4 的规则；重试中产生的拒绝记录也要并入 | 部分实现，联动未测 |
| dev-1.14 的候选森林 | 只在"有 required 反亲和且作业没有硬拓扑"时启用，允许不同的子组落在不同的剩余域里；单个子组仍然要落在一个域里 | 先保留森林，森林找不到解时才按可用域搜索。这样现在能调度的作业落位不变 | 已实现并实测；直接替换森林的做法见 §10 |
| dev-1.14 的 required SubGroup 反亲和 | 与 PodGroup 反亲和一起按名字过滤 | 也属于可用域，但范围是子组一级，并且随同一作业里已放下的同伴变化 | 未做原型 |
| 开关回退 | — | 经可用域跨域放置的作业，在关掉开关或没有这个特性的调度器上无法补 Pod，表现与修复前的缺陷相同；运行中的 Pod 不受影响。需要写进升级说明 | 实测 |

## 8. 分期与开关

每一步有独立开关，默认关闭。"落位"指 Pod 到节点的映射。

| 步骤 | 内容 | 现在能调度的作业，落位是否变化 | 其他可见变化 | 需要单独批准 |
| --- | --- | --- | --- | --- |
| 1 | 把探测测试整理成仓库内的表征测试 | 否 | 无 | — |
| 2 | 并列键 `hash(单元 UID, 域名, 轮次)`，用于 Job 级、子组级、节点级 | 并列时从随机变为固定，结果仍在现行允许的范围内 | 无拓扑的作业也受节点级并列键影响 | 默认值 |
| 3 | 排序 → 验证：子组级，以及没有 SubGroup 策略的作业的 Job 级；胜者不重放 | 否。已知例外见 §4.3.4 | 带待分配 DRA claim 的这类作业从失败变为成功；试放写入的指标计数下降 | — |
| 4 | 资源必要条件 | 否 | 不可调度时的状态文本变化：被跳过的候选不再试放，原来显示为 `Schedulable` 的 Pod 会显示为 `Unschedulable` | 文本 |
| 5 | 决策记录的输出 | 否 | PodGroup 条件消息的内容变化；新增日志和指标 | 格式 |
| 6 | 可用域：筛选、总量检查、打分、落位记录、摘要、提名与抢占路径（§4.2.2、§7） | 单个作业：否。同一周期里排在后面的作业可能受影响（§10.2） | **现在调度不了的作业变为可调度**（§5.3 的表） | 是：语义变更 |
| 7 | 找不到解时的有限重试 | 单个作业：否。同一周期里排在后面的作业可能受影响（§10.2） | **现在调度不了的作业变为可调度**；失败路径的成本上升，有上限 | 是 |
| 8 | SubGroup 作业的 Job 级排序 | **是**：同层有多个可行域时，选中的域可能不同（实测 5%–9% 的作业，§4.3.6） | 随机作业流里任务试放次数少约四成，1024 节点基准上耗时降一个量级；SubGroup 作业不再重放（原型尚未实现这一点） | 是 |
| 可选 | 已有任务占比改为独立的排序键；节点偏好项；换层之前先重试；dev-1.14 用可用域替换森林 | 是 | — | 各自单独批准 |

顺序上的三条约束：

- 步骤 2 的并列键必须从一开始就带轮次。固定而不带轮次的并列键，会让靠并列运气才能调度的作业从"几个周期内调度"变成"永远调度不了"（§10.1）。
- 步骤 6、7 与步骤 2–5 相互独立，可以先做。它们修的是现存缺陷。
- 步骤 8 依赖步骤 3。

另有一项不改语义的降本可以随时做，目前没有原型：域的空闲资源改为增量维护（第一轮原型的一次 CPU 剖析里，重复累加域内节点资源占 allocate 耗时约 31%；剖析文件没有保留）；NTA 的事件回调改用"节点到所属域"的反向索引。

产品化时必须补上、原型没有做的：开关在每个调度周期按配置重新取值；决策记录设上限并在每个周期重置；并列键的轮次按作业维护；去掉原型的环境变量入口。

| 重试 | 预算按"每作业每周期"计；可用节点相同的候选域只重试一次；重试失败后，条件文本、任务状态、失败原因与不开重试时相同；弹性 gang 重试成功后没有残留的子组落位记录；预算用完时有"搜索未完成"的记录；重试成功与失败时的拒绝记录 |

| 插件兼容 | 待分配的 DRA claim 加两个可行域，胜者不是最后试放的那个；拒绝缓存打开时，兄弟域或被跳过的域释放资源后作业被唤醒；提名域在可用域内被接受、含被排除节点时被拒绝；带 task-topology 注解的硬拓扑作业 |
| 开关 | 开关全关时新分支不可达；从配置里删掉开关键后行为回到默认 |

项目门禁（`make unit-test`、`make lint`、`make verify` 或各基线的等价命令）照常运行。

### 9.3 基准

成功路径和失败路径分开测。节点千级、域百级。另测：候选组合在 2 千和 1 万个域时的耗时；可用域过滤的耗时；一个长期调度不了的作业每个周期重复重试的稳态开销。验收门槛在取得生产上两条路径的比例之后再定。

## 10. 风险、限制与待决定的事项

### 10.1 评审发现并已纳入设计的问题

设计稿经过两个独立子代理的评审（方案分析、客户行为与回归分析）。下面是它们发现、并且改变了设计的问题。原始报告见附录 A 的"评审"。"证据"一列的数字来自评审报告，测的是修正之前的第二轮原型；"修正后"的数字来自最终的原型。

| 问题 | 证据 | 设计上的处理 |
| --- | --- | --- |
| 固定的并列键会让靠并列运气调度的作业永远调度不了。现行的随机并列相当于每个周期换一种顺序重试 | 16 个作业、每个 12 个周期：现行全部调度成功；不带轮次的固定并列键下，8 个始终调度不了 | 并列键带轮次（§4.3.8）。带轮次后 16 个全部在 9 个周期内调度 |
| 重试失败后，用户看到的状态变得乐观而且是错的：一个无解的作业显示成"3 个任务可调度" | 条件文本从 `2/3 tasks in gang unschedulable` 变成 `0/3` | 重试失败后恢复正常搜索结束时的失败原因和任务状态。修正后三种预算下的文本逐字相同 |
| 重试的预算浪费在重复的搜索上：可用节点相同的两个候选域各试一遍；第一个子组就放不下的尝试也扣预算 | 918 次重试里 431 次在第一个子组就结束 | 按可用节点去重；第一个子组就放不下的尝试不计入预算；预算按每作业每周期计。修正后同一批场景在预算 4 时的漏解从 5 个降到 4 个（混合）、保持 1 个（争用） |
| 弹性 gang 重试成功后，没放下 Pod 的子组带着失败那次试放留下的落位记录，本周期内它的 Pod 放不到别处 | 重试后 2/3，对照 3/3 | 每次 Job 级试放之前清掉这个候选域里上一次留下的子组记录。修正后 3/3 |
| 可用域生效后，被部分排除的父域带着不能用的资源通过总量检查，无解的反亲和作业每个周期都被试放 | 试放次数从 0 变成 10–15 | 总量检查按可用节点计算（§7） |
| 可用域的组合按域名做，遇到两个粒度不同的来源、或者子组级的排除时不成立 | 读码推断 | 可用域定义为节点集合，按单元分层生效（§4.2.2） |
| "现在能调度的作业落位不变"对可用域成立，靠的是 required 反亲和现在拒绝一切比比较层更粗的候选，所以新增的候选都在更宽的层。这不是框架保证的 | 读码 | 写成对可用域提供方的要求（§4.2.2），实施时加断言和单测（§9.1） |

两个评审子代理写在 allocate 包里的 16 个探测，已在修正后的上游原型上重跑并全部通过。没有重跑的有：group-topology-affinity 包里的提名探测，以及行为分析子代理在 dev-1.14 上的探测。重跑的探测里，方案分析子代理的随机测试比本文的更宽：2000 个场景，包含弹性 gang、soft 拓扑、多条反亲和条目、没有公共父域的拓扑；另有 593 个"作业已部分运行、再扩容"的场景。结果是现行能调度而丢失 0、落位变化 0、非法落位 0。

### 10.2 已知的限制

| 项 | 说明 |
| --- | --- |
| 没有 Kind 验证 | 全部结论止于单元测试。随机场景不超过 64 个节点，与暴力求解器对照的场景不超过 20 个节点 |
| 保证只对单个作业成立 | 一个作业新变成可调度后会占用资源和域。同一个周期里排在后面的作业可能因此落空。实测两种情形：资源被占（600 个会话里 7 个）；两个互相 required 反亲和的作业，排在前面的现在能用掉剩下的全部域，排在后面的无处可放 |
| 失败路径的成本 | 排序不减少失败路径的试放；可用域增加候选，重试再增加一部分。在现行调度不了的场景里，开启可用域和预算 4 的重试后，任务试放次数比只做排序多 25%（争用场景）和 48%（混合场景）；与现行相比是少 34% 和多 10% |
| 域内任务大小不一造成的漏解 | 不处理。并列键的轮次能覆盖其中"靠并列运气"的那部分 |
| 重试不完备 | 只调整子组的先后，不换子组选的域。本次的对照场景里预算足够时没有剩余，不能据此推断生产负载 |
| 节点抽样 | 域内节点超过 100 个时启用抽样，游标会被试放次数推进。新旧流程在这种域里选到的节点可能不同，"不丢可调度性"的论证（§5.3）在这种域里也没有验证。测试避开了大域 |
| 确定性的范围 | 只覆盖 allocate。抢占、回填仍然用随机数 |
| 第三方 `HyperNodeOrderFn` | 依赖试放副作用或候选集合的打分会受影响，无法枚举 |
| 原型没有覆盖的部分 | §7 表里标为"未实现""未改""未做原型"的各项；SubGroup 作业 Job 级排序后保留试放结果（原型仍然重放）；并列键的轮次按作业维护（原型用一个全局值，由测试设置）；可用域按节点集合表示、按单元分层生效（原型仍按域名表示，每个作业只设一次） |
| 生产上成功路径与失败路径的比例 | 未知，决定实际收益 |

### 10.3 需要决定的事项

1. **可用域语义。** 是否批准把 required PodGroup 反亲和解释为"只排除域；更粗的域作为容器合法，只能使用未被排除的部分"。上游设计文档现在的表述相反。不批准的话，用户报告的缺陷只能继续按场景修补。
2. **互相反亲和的作业的先后。** 是否接受 §10.2 第二行的后果：两个互相反亲和的作业，排在前面的现在能把剩下的域用完。这是修复漏解的直接结果，按优先级顺序看是正确的，但它改变了今天"前面的作业调度不了、后面的小作业能调度"的结果。
3. **重试是否启用，默认预算多少。** 建议 4 次，留 1 次给最宽的候选域。
4. **SubGroup 作业的 Job 级是否排序**（§4.3.6）。
5. **并列键的轮次**取"该作业连续调度失败的周期数"是否可以接受。它让第一次尝试完全可复现，之后每失败一个周期换一种并列顺序。
6. **先做哪条基线。** dev-1.14 多出候选森林。建议在 dev-1.14 上先采用"森林优先"。直接用可用域替换森林，600 个随机场景里有 26 个作业的落位改变（现行能调度的 464 个的 5.6%），都变得更集中；但它需要先修通用路径上弹性 SubGroup 作业的落位记录，而且受影响的作业在成功路径上的任务试放次数增加：排序模式下，历史缺陷的三个变体是 4→12、4→8、4→12 次，一个域就放得下的对照作业是 2→8 次；每个候选都试放的模式下评审测得 1.4–2 倍（10→20、6→10、7→10）。
7. **三个可选项**是否要做：已有任务占比改为独立的排序键；节点偏好项；换层之前先重试（它需要独立的预算，与最终重试共用预算时，小预算下反而少调度作业）。
8. **域内任务大小不一的漏解**是否纳入本次重构。
