# 拓扑调度重构：本轮诉求与设计评价标准

日期：2026-09-11。依据本 session 的连续要求、用户最新纠正，以及015博客中的原始目标整理。本文先确定需要解决的问题和评价标准，不预先选定算法，不表示进入实现阶段。

## 1. 核心诉求

设计一个能在大规模生产集群中运行的通用拓扑调度框架，以一致的模型和流程处理 hard、soft、多 SubGroup 关系及普通调度偏好的组合，在可控成本内获得高质量放置，并且便于运维理解和理论分析。

框架的价值应体现在：许多表面不同的场景都是同一套约束、目标和决策机制的实例；遇到新的组合时，主要改变输入和策略声明，核心调度过程仍然成立。

Bug020 和其他案例用于检验这种通用性。不能从某个案例所需的特殊操作出发，把逐项补救包装成新架构。

## 2. 讨论对象与资料地位

- **015的目标重构方案仍处于设计讨论阶段。** 本轮是从目标和源码重新评估、优化架构，不能按“已实施015，需要补丁修复”组织论证。
- 当前源码用于确认现有语义、调用链、代价、插件协作和实际修改边界。历史实验、分支和局部修复记录只提供证据，不代表目标架构已实施。
- `TOPOLOGY_SCHEDULING_REFACTOR_BLOG.md` 中的目标值得继承，其中的具体设计选择可以重新评估。例如首个可行方案后是否继续探索，应由本轮质量与成本目标决定，不能将旧文结论当作不可改变的需求。
- 本轮交付是新的、可独立阅读的完整方案。旧方案的差异说明可以作为附录，不能成为正文主线。
- 本轮没有要求修改 Volcano 实现，也没有要求部署、运行生产变更或提交实现代码。

## 4. 从这些要求推导出的设计评价标准

以下是工程推导，用于评判候选设计，不是用户已指定某种算法。

### 4.1 先定义优化目标，再讨论搜索方法

“更优”需要明确主体、比较范围和评分口径。单个 Pod 的高分、某个 SubGroup 的紧凑程度、整个 PodGroup 的综合收益，不能未经说明就视为相同目标。

多个偏好同时存在时，应能解释权重、归一化、计数单位及组合结果。局部决策评分是否可以累计为完整放置收益，必须经过论证。不能用“拓扑更好”覆盖用户启用的 Binpack 或其他普通偏好，也不能将某个案例中的均匀分布直接当作通用最优标准。

首个可行方案、有限预算内的较好方案和完整问题的全局最优，是不同质量等级。应明确设计提供哪一种能力、什么条件下能够提供更强保证。

### 4.2 单一模型自然产生组合行为

策略负责表达事实、约束和偏好；规划机制负责选择、状态推进和停止。主流程不应出现以 Bug 编号、特定 workload role 或某种插件组合命名的调度分支。

资源异构、peer 数量、多个 SubGroup、多个拓扑范围应进入模型本身。不能遇到一个案例就增加一个专门的 fallback、交换模板或修复流程。

未来新增一种业务语义可能需要 provider 或 evaluator；通用性的标准是它能通过稳定边界接入，而不是所有未来策略都无需编写代码。

### 4.3 顺序应作为效率因素被治理

要分别评价两类问题：局部选择造成后续无法放置；所有任务都能放置但联合收益较差。只覆盖前者，不足以满足本轮要求。

也不能直接假设“调整 SubGroup 顺序”就是答案。候选设计需要说明，改变输入顺序如何影响搜索成本和有限预算结果；什么条件下最终可行性或最优性不依赖顺序。

### 4.4 通用覆盖与无条件保证分开

“同一架构能处理很多场景”要求模型有表达能力、算法能够探索相关方案，并通过统一验证证明有效。它不等于要求任意规模、任意约束组合都能在固定短时间内求得全局最优。

但不能仅以“有预算，所以不保证”为理由回避效果。必须通过代表性场景族、相同预算下的比较和可复现实验，说明一般情况下的收益及困难边界。

### 4.5 效率分析覆盖真实工作

时间复杂度至少区分：

1. 快照准备、策略编译与共享索引建立，以及这些成本的摊销范围。
2. 候选生成、hard 检查、普通 Predicate、逐节点和批量评分。
3. 状态维护、关系传播、搜索、撤销、恢复与终态校验。
4. 最好成功路径、候选稀疏/无解路径及组合搜索最差情况。
5. 截断机制实际约束哪些工作，以及停止和恢复本身需要的额度。

任务数、节点数、拓扑规模、关系密度、资源维度、候选样本和插件内部成本，不能未经假设全部吸收到“常数”中。时间之外还应分析空间、缓存增长和调度延迟尾部；并行降低部分延迟，不等于总工作量相应减少。

### 4.6 数学证明和运维解释对应同一过程

数学模型应由实际问题决定。物理拓扑是树，不自动说明完整调度问题具有树上的多项式算法；“快速子图搜索”是研究线索，不是预定的建模结论。

证明应覆盖明确性质，例如 hard 安全、剪枝不误删合法扩展、状态恢复、特定条件下的完备性、质量保证和成本上界。必须把模型定理、实现合同、模型验算与实际 Volcano 验证分开。

运维描述应能对应这些性质：在哪个范围内检查了哪些候选，什么约束或评分影响了决定，以及停止时还剩下什么不确定性。解释能力应来自稳定的决策步骤和状态，而不依赖还原大量特殊分支。

### 4.7 修改范围作为架构选择的一部分

优先利用现有 Predicate、评分入口、调度优先级、Gang/Ready 和状态事务边界；需要改变某个边界时，应说明其必要性、收益和验证成本。

“范围可控”不能被解释为只能在旧结构上加条件判断；“通用框架”也不能成为全面重写插件和调度器的理由。比较候选架构时要把实现侵入性、维护成本和运行成本一起考虑。

## 5. 尚需由方案明确的选择

这些是本轮研究应给出理由的设计决定，不要求用户先选算法：

- 联合目标的确切作用范围，以及与现有准入、任务优先级和弹性任务的关系。
- 局部排序与整体质量评价的合同，历史评分行为的兼容方式。
- 能同时处理可行性和质量问题的主算法，以及利用拓扑/约束结构减少工作的方式。
- 预算、采样、停止规则和对用户可见的质量保证。
- 初始实施边界，以及哪些增强能力可以后续通过同一接口加入。

## 6. 下一份完整方案的组织方式

正文按“目标与边界 → 统一模型 → 核心流程 → 结构性提效 → 正确性与复杂度 → 场景验证 → 修改范围”展开。

场景验证需要将不同案例映射回同一组规则和状态转移。例如：不连续域候选、多层拓扑、required/preferred 混合、多 SubGroup 资源竞争、多来源评分，以及 Bug020。重点展示相同机制如何产生合适结果，而不是逐项说明新增什么修复动作。

旧方案差异放入附录。已经形成的中间分析只作为研究材料，按本文诉求重新取舍，不作为必须保留的架构结论。

## 7. 本轮纠偏记录

此前分析以“Bug020需要更大的联合交换，因此新增调整范围扩展机制”组织建议，容易将方案导向案例驱动的补救。这不符合用户对通用架构的要求。后续应从统一约束优化问题、可组合语义与实际代价推导机制，再由 Bug020 检验其覆盖和效率。

同样，不能将015目标方案描述为已经实施并需要修补。本 session 的最新明确要求优先于历史任务记录中的阶段性表述。

## 8. 本轮追加要求：直观合同与新旧速度

用户进一步要求：先不看调度结果，回答重构与当前实现哪一个更快；若有劣化，说明为了更好目标多花多少；在回答过程中继续打磨方案。

因此需将基础首解成本与首解后质量成本分别对账，包含候选检查、全部评分、编译/传播、状态更新、撤销与最终恢复。先给源码能支持的计数和带条件公式，目标未实现时不能杜撰实测百分比。理论最好/最差复杂度继续保留，不能用它代替实际单价与尾部延迟。

组件合同要能以日常语言解释，并映射回接口、状态与证明。性能打磨不能通过删去 hard/soft 组合、多 SubGroup 整体质量或普通评分协作来缩减本次目标。
